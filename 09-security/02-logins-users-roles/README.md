# Имена входа, пользователи и роли

Логин (login) — субъект уровня экземпляра, пользователь (user) — уровня базы, роль (role) объединяет разрешения. Частый вариант — сопоставить пользователя логину по SID, внутреннему идентификатору безопасности. Совпадение имён не всегда означает совпадение SID.

В будущей учебной базе, при заранее созданном логине `LabReaderLogin`:

```sql
CREATE USER LabReader FOR LOGIN LabReaderLogin;
CREATE ROLE LabReportReaders;
ALTER ROLE LabReportReaders ADD MEMBER LabReader;
GRANT SELECT ON SCHEMA::Sales TO LabReportReaders;
```

Здесь предполагается существующая схема `Sales` с учебными объектами. Команды показывают модель назначения, а не автоматически готовую конфигурацию AdventureWorks. Доступ на всю схему распространяется на её объекты; если нужен один отчёт, такой грант может быть шире необходимого.

**Пример после restore.** Пользователь базы сохранился с исходным SID, а новый логин того же имени получил другой SID. Возникает осиротевший пользователь (orphaned user). Для исправления сопоставления применяют `ALTER USER ... WITH LOGIN = ...` после проверки личности. Не удаляйте пользователя вместе с его владением объектами без анализа.

Фиксированные роли вроде `db_owner` дают широкие возможности. Для прикладных задач чаще удобна собственная роль с конкретным `SELECT` или `EXECUTE`. Участие в серверной роли не равно участию в роли каждой базы.

**Самопроверка.** Достаточно ли backup одной пользовательской базы для переноса логинов и заданий? Нет: их серверные сведения нужно перенести отдельно, сохранив необходимые SID и права.
