# Разрешения и цепочки владения

`GRANT` выдаёт разрешение, `DENY` запрещает, `REVOKE` убирает ранее заданную запись разрешения. Revoke не равен deny: доступ может сохраниться через роль. У DENY есть исключения и особенности иерархии; `sysadmin` не является подходящим субъектом для проверки запрета.

```sql
SELECT *
FROM fn_my_permissions(N'Sales.SalesOrderHeader', N'OBJECT');
```

Запрос показывает эффективные разрешения текущего пользователя на объект. Проверять доступ приложения нужно в его контексте и с его членствами в ролях. Разрешение на схему может охватывать больше объектов, чем разрешение на одну процедуру.

Цепочка владения (ownership chain) позволяет процедуре обращаться к объектам того же владельца без отдельной проверки прав вызывающего на каждый объект в типичном статическом сценарии. Это даёт интерфейс `EXECUTE` без прямого чтения таблиц. Цепочка не является универсальным обходом всех проверок; динамический SQL, разные владельцы и разные базы меняют условия.

**Пример.** Роль приложения может вызывать `dbo.CreateOrder`, но не делать произвольный `UPDATE` таблиц заказов. Процедура проверяет параметры и реализует транзакцию. Если она собирает непроверенный динамический текст под повышенным контекстом, узкий интерфейс перестаёт быть защитой.

**Ошибка:** включать `TRUSTWORTHY` или межбазовые широкие полномочия только ради исчезновения ошибки. Сначала спроектируйте требуемый доступ; для сложных сценариев рассматривают подпись модуля сертификатом с точными разрешениями.

**Самопроверка.** Удалили прямой `GRANT SELECT`, но чтение работает. Почему? Проверьте роли, разрешения схемы и более высокие уровни.
