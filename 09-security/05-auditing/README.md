# Аудит SQL Server

SQL Server Audit фиксирует выбранные действия безопасности. Server Audit задаёт, куда писать события; server/database audit specification определяет, какие действия отслеживать. Создание спецификации и фактическое включение сбора — отдельные шаги.

**Пример.** Нужно знать, кто читал таблицу зарплат и кто менял права. Определите объекты, типы действий, субъекты и хранилище. Сбор всех запросов всех баз быстро создаёт большой журнал и может хранить лишние чувствительные сведения.

В подготовленном SQL Server 2014 Enterprise используйте SSMS → Security → Audits и соответствующие спецификации. Для лаборатории проверьте успешный и запрещённый доступ отдельным тестовым пользователем, затем прочитайте audit-файл. Тест административным логином не воспроизводит права приложения.

Набор аудируемых действий и уровни разрешений проверяйте именно для 2014. Аудит — не таблица истории всех предыдущих версий бизнес-строки. DML-триггер, Change Data Capture, журнал транзакций и Audit имеют разные назначения и гарантии.

Продумайте доступ к журналам, целостность, срок хранения, место и поведение при отказе записи. Выбор остановки операции или продолжения при недоступном аудите влияет на доступность и должен быть осознанным.

**Ошибка:** считать факт «аудит включён» доказательством, что нужное событие сохраняется и доступно через месяц. Проверьте конкретное действие, успешность записи, ротацию файлов и процедуру чтения.

**Самопроверка.** Защитит ли аудит от SQL injection? Он может помочь расследованию, но предотвращение требует параметризации и минимальных прав.
