# Ключи и ограничения целостности

Ограничение (constraint) проверяет правило на стороне базы. `PRIMARY KEY` идентифицирует строку, `UNIQUE` запрещает повтор ключа, `FOREIGN KEY` проверяет ссылку, `CHECK` — условие, `NOT NULL` запрещает неизвестное значение. `DEFAULT` поставляет значение при вставке, но сам по себе не ограничивает диапазон.

```sql
CREATE TABLE #OrderLine
(
    OrderID int NOT NULL,
    LineNo int NOT NULL,
    ProductID int NOT NULL,
    Qty int NOT NULL CHECK (Qty > 0),
    PRIMARY KEY (OrderID, LineNo)
);
INSERT INTO #OrderLine VALUES (1, 1, 707, 2);
-- Вставка (1, 1, 708, 3) нарушила бы первичный ключ.
-- Количество 0 нарушило бы CHECK.
```

В постоянной учебной схеме добавьте внешний ключ `ProductID` к таблице товаров той же базы. SQL Server не обеспечивает внешние ключи временных таблиц, поэтому пример не изображает такую защиту в `#OrderLine`.

`CHECK (Qty > 0)` без `NOT NULL` допускает `NULL`, потому что неизвестный результат не является `FALSE`. Первичный ключ не допускает `NULL`; обычное уникальное ограничение на одном столбце в SQL Server допускает лишь одно `NULL`.

Создание внешнего ключа не создаёт автоматически индекс на дочернем столбце. Индекс может быть полезен для соединений и проверок удаления родителя, но это отдельное решение о производительности.

**Ошибка:** включать каскадное удаление без анализа. Удаление покупателя не должно неожиданно уничтожить историю продаж. Сначала определите бизнес-правило и допустимую историю.
