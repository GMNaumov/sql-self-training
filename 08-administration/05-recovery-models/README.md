# Модели восстановления и журнал транзакций

Модель восстановления (recovery model) определяет работу журнала и возможности backup/restore, а не общую «надёжность базы». В SIMPLE неактивная часть журнала обычно становится доступна для повторного использования после checkpoint, если другие причины не удерживают её. Log backup для восстановления на время здесь не используется.

FULL поддерживает цепочку журналов и point-in-time. После перехода из SIMPLE нужно начать новую цепочку backup данных. В FULL отсутствие регулярных log backup может приводить к росту журнала. BULK_LOGGED допускает минимальное журналирование некоторых массовых операций при условиях; это не полное выключение журнала.

```sql
SELECT name, recovery_model_desc, log_reuse_wait_desc
FROM sys.databases
WHERE name = N'AdventureWorks2014';
```

**Пример.** `.ldf` растёт, `log_reuse_wait_desc = LOG_BACKUP`: проверьте расписание и результат резервирования журнала. Если `ACTIVE_TRANSACTION`, найдите длительную транзакцию. Одинаковый симптом роста имеет разные причины.

При BULK_LOGGED журналовая копия, содержащая минимально журналированные операции, может не позволить остановиться на произвольном моменте внутри неё: потребуется восстановить до её конца. Переключение FULL ↔ BULK_LOGGED само по себе не аналогично переходу через SIMPLE, но влияет на гарантии цели.

**Ошибка:** считать checkpoint уменьшением файла или использовать shrink вместо устранения причины. Усечение означает освобождение внутреннего места для повторной записи; физическое уменьшение — другая операция.

**Самопроверка.** Нужно ли всегда выбирать FULL? Требования к потерям и операциям определяет бизнес; вместе с FULL нужна работающая стратегия log backup.
