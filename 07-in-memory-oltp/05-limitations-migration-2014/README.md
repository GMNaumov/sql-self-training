# Ограничения и миграция в SQL Server 2014

Миграция начинается с выбора действительно горячей таблицы и доказанного узкого места. Сначала измерьте обычное решение с корректными индексами и короткими транзакциями. Если время уходит на передачу миллионов строк, перенос маленького справочника в память не устранит причину.

Для SQL Server 2014 заранее проверьте: типы и размер строк, отсутствие неподдерживаемых LOB-типов вроде `nvarchar(max)`, ограничения индексов, отсутствие привычной поддержки `ALTER TABLE`, внешних ключей и `CHECK` для memory-optimized таблиц этой версии. Строковые индексные ключи имеют ограничения сопоставления; не переносите современный пример без проверки. Объём устойчивых данных, индексы, версии и запас под восстановление нужно планировать по ограничениям первой реализации, а не по пределам In-Memory OLTP новых версий.

**План для состояний заказов:** выбрать небольшой объект; проверить Memory Optimization Advisor; спроектировать ключи; создать новую таблицу в отдельной базе; перенести копию данных; адаптировать доступ и обработку конфликтов; проверить длительную конкурентную нагрузку, резервирование и рестарт; подготовить возврат к исходной схеме.

После миграции сравните не только одну выборку, но и запись, память, журнал, длительность запуска и работу восстановления. Если ограничения целостности больше не поддерживаются движком таблицы, нужно явно объяснить, где и как обеспечивается правило; молча удалять его нельзя.

**Ошибка:** массово преобразовать все таблицы AdventureWorks. Механизм имеет собственные ограничения и не является новым значением обычного параметра хранения. Тестирование и обратимость обязательны для технического обоснования, даже если учебный пример мал.
