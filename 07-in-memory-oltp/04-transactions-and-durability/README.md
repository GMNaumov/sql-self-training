# Транзакции и устойчивость данных

Устойчивость (durability) и изоляция (isolation) решают разные задачи. `SCHEMA_AND_DATA` сохраняет данные memory-optimized таблицы через журнал и checkpoint; `SCHEMA_ONLY` сохраняет схему, а строки после перезапуска исчезают. У обоих режимов есть транзакционные правила и контроль конфликтов.

**Пример выбора.** Подтверждённый заказ нельзя хранить только в `SCHEMA_ONLY`, если другого надёжного источника нет. Пересчитываемый кеш временных результатов может пережить потерю строк, если приложение умеет восстановить его.

Для явных транзакций доступ к memory-optimized данным должен учитывать поддерживаемую изоляцию. Например, в подготовленной лаборатории:

```sql
BEGIN TRANSACTION;
SELECT OrderID, Status
FROM dbo.LabOrderState WITH (SNAPSHOT)
WHERE OrderID = 123;
COMMIT TRANSACTION;
```

Это пример согласованного чтения, а не алгоритм резервирования. Политика повторов должна учитывать конфликты записи и проверки зависимостей, например ошибки семейства 413xx. Не повторяйте все ошибки подряд: синтаксическая ошибка или нехватка памяти требуют другого действия.

Отложенная устойчивость (delayed durability), появившаяся в 2014, может подтвердить commit до физической записи соответствующего журнала и допускает потерю недавних подтверждённых транзакций при сбое. Она не тождественна `SCHEMA_ONLY`, где теряется всё содержимое таблицы после рестарта.

**Самопроверка.** Достаточно ли отсутствия lock-wait для успешной конкурентной работы? Нет: измеряйте конфликты, повторы, задержки и фактическую пропускную способность.
