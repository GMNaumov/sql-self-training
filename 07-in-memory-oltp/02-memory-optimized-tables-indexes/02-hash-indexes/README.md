# Хеш-индексы (hash indexes) и выбор числа корзин

Хеш-индекс (hash index) вычисляет корзину (bucket) по ключу. Он эффективен для равенства по полному ключу. Разные ключи могут попасть в одну корзину — возникает цепочка коллизий. Длинные цепочки увеличивают работу поиска.

**Пример.** Для `OrderID = 123` уникальный hash-ключ хорошо соответствует задаче. Для `CreatedAt >= @date` hash не даёт нужного диапазона. У составного hash `(CustomerID, OrderID)` одного равенства по `CustomerID` недостаточно для полного хеш-поиска.

Число `BUCKET_COUNT` выбирают по ожидаемому числу различных значений ключа, а не только по строкам. При 100 тысячах уникальных заказов отправная оценка порядка 100–200 тысяч корзин разумнее 1024; движок округляет число к степени двойки. Слишком мало корзин — больше коллизий, слишком много — лишняя память. Миллион одинаковых статусов не станет хорошим hash-индексом от миллиона корзин.

В подготовленной базе можно исследовать:

```sql
SELECT object_id, index_id, total_bucket_count,
       empty_bucket_count, avg_chain_length, max_chain_length
FROM sys.dm_db_xtp_hash_index_stats;
```

Сопоставьте заполненность и цепочки с повторами ключа и рабочими запросами. Для чтения диагностики нужны соответствующие права.

В SQL Server 2014 менять определения memory-optimized индексов существенно сложнее, чем в новых версиях; планируйте пересоздание и перенос. **Ошибка:** увеличивать корзины для плохого диапазонного запроса. Нужно выбрать другой тип индекса, а не только его размер.
