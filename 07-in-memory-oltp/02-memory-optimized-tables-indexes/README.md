# Оптимизированные для памяти таблицы и индексы

Таблица в памяти задаётся `WITH (MEMORY_OPTIMIZED = ON, DURABILITY = ...)`. Для устойчивых строк используется `SCHEMA_AND_DATA`; для восстанавливаемой приложением рабочей области может подходить `SCHEMA_ONLY`. Это решение о потере данных после рестарта, а не просто о скорости.

В SQL Server 2014 индексы объявляются внутри `CREATE TABLE`; обычное последующее `CREATE INDEX` не подходит. Таблица должна иметь индекс, а для `SCHEMA_AND_DATA` необходим первичный ключ. Максимум — восемь индексов. Для изменения структуры в этой версии часто нужна новая таблица и перенос, а не привычный `ALTER TABLE`.

**Пример выбора ключей.** Для состояния заказа нужен точечный поиск по `OrderID` и список по дате. Первый запрос может использовать hash по уникальному ключу, второй — memory-optimized nonclustered индекс по дате. Hash не заменяет диапазонный индекс.

Индексы в памяти ссылаются на версии строк и не устроены как листовые страницы дискового индекса. Не добавляйте `INCLUDE` по аналогии с rowstore: для memory-optimized индексов доступ к столбцам устроен иначе.

**Контроль проектирования:** ожидаемое число строк и уникальных ключей, равенства и диапазоны, долговечность, допустимые типы и затраты памяти. Наличие объектов с похожими именами в примерах не означает, что они уже есть в AdventureWorks.

Сведения о первой реализации: [индексы In-Memory OLTP 2014 от команды SQL Server](https://www.microsoft.com/en-us/sql-server/blog/2013/11/12/sql-server-2014-in-memory-oltp-nonclustered-indexes-for-memory-optimized-tables/).
