# Некластеризованные индексы для диапазонного доступа

Memory-optimized nonclustered индекс организует упорядоченный доступ и подходит для диапазонов и поиска по ведущей части ключа. Его реализация отличается от дискового B-tree; не переносите сюда рассуждения о дефрагментации страниц rowstore.

Для таблицы `dbo.LabOrderState` из урока создания:

```sql
DECLARE @From datetime2 = '20140101';
SELECT OrderID, Status, CreatedAt
FROM dbo.LabOrderState
WHERE CreatedAt >= @From AND CreatedAt < '20140201'
ORDER BY CreatedAt, OrderID;
```

Индекс `IX_CreatedAt` позволяет искать временной диапазон. Дополнительная сортировка по `OrderID` гарантирует порядок строк с одинаковым временем; для её полного покрытия порядком можно заранее спроектировать составной ключ `(CreatedAt, OrderID)`.

**Пример выбора.** Очередь заказов должна отдавать самые старые неподтверждённые элементы. Продумайте индекс по признаку состояния и времени и конкурентное получение элемента; один индекс не делает выбор и изменение атомарными. Нельзя просто переносить блокировочные приёмы очереди с `READPAST` на движок с другой моделью доступа.

Индексы объявляются при создании таблицы в SQL Server 2014. Их память входит в общую ёмкость In-Memory OLTP; лишний индекс также увеличивает работу записи. Упорядоченность индекса не даёт права убрать `ORDER BY` из договора выдачи.

**Самопроверка.** Всегда ли hash быстрее nonclustered? Нет. Он удобен для полного равенства по подходящему ключу; для диапазона, сортировки или неполного ключа чаще нужен другой доступ.
