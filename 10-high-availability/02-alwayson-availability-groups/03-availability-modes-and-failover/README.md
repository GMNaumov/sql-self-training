# Режимы доступности и переключение реплик

В синхронном режиме (synchronous commit) основная при нормальной связи ждёт подтверждения сохранения журнала синхронной secondary. Это не ожидание выполнения redo каждой строки. В асинхронном (asynchronous commit) commit не ждёт удалённого сохранения, поэтому возможна потеря ещё не доставленного журнала.

**Пример.** Реплика в том же ЦОД добавляет небольшую сетевую задержку и подходит для локальной HA. Удалённая площадка с большой задержкой может потребовать asynchronous и допустимый RPO. Если синхронный партнёр недоступен, поведение основной и гарантии нужно оценивать по фактическому состоянию и тайм-аутам.

В SQL Server 2014 до трёх реплик могут быть настроены synchronous commit, считая primary и до двух secondary. Автоматическая failover-пара ограничена двумя репликами. Для автоматического переключения нужны соответствующие настройки, синхронизированное состояние, работоспособный WSFC и условия политики отказа.

Плановое переключение без потери и принудительное с возможной потерей — разные операции. Принудительное продвижение отставшей secondary может оставить подтверждённые клиенту заказы на прежней основной; нужен план сверки и предотвращения конфликтующего повторного ввода.

**Лабораторный критерий:** измерьте reconnect приложения, log send queue и redo queue, наличие контрольных заказов и продолжение заданий. Смена роли базы не переносит все серверные задачи автоматически.

**Ошибка:** считать `SYNCHRONOUS_COMMIT` равным постоянному `SYNCHRONIZED`. Первая строка — конфигурация, вторая — состояние, которое может измениться.
