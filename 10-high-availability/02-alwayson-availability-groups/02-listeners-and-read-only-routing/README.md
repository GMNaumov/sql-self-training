# Прослушиватели (listeners) и маршрутизация чтения

Прослушиватель (listener) — сетевое имя и адреса для подключения к роли AG, а не к конкретному серверу. При переключении приложение должно переподключиться через listener. Открытое TCP-соединение не превращается автоматически в новое без ошибки.

**Пример строки подключения** для подходящего драйвера: `Server=AWListener;Database=AdventureWorks2014;Integrated Security=True;ApplicationIntent=ReadOnly;`. Для нескольких подсетей рассматривают `MultiSubnetFailover=True` с учётом поддержки драйвера. Это описание будущей инфраструктуры, не готовое имя сервера проекта.

Read-only routing требует читаемой вторичной реплики, routing URL и списка маршрутизации у возможных основных реплик. Клиент должен подключаться к listener, указывать базу группы и намерение чтения. Само `ApplicationIntent=ReadOnly` не создаёт настройку маршрутизации.

В SQL Server 2014 используется упорядоченный список маршрутизации, без round-robin балансировки чтения, добавленной позже. Нельзя обещать равномерное распределение по всем secondary.

Отчёт на secondary может видеть отставшее состояние из-за очереди redo. Договоритесь, допустима ли эта задержка. Сценарий «записать заказ и сразу прочитать его» может требовать основной реплики.

**Ошибка:** приложение продолжает подключаться по имени старого primary, хотя listener настроен. Проверьте фактическую строку подключения, DNS, драйвер, имя сертификата и логику повторов.

**Самопроверка.** Является ли listener прокси, передающим все запросы между репликами? Нет: он обеспечивает точку подключения и участвует в механизме соединения и перенаправления; это не универсальный балансировщик SQL-команд.
