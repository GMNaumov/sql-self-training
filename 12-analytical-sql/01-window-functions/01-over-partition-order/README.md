# Предложение OVER: PARTITION BY и ORDER BY

`PARTITION BY` делит вход на независимые группы для расчёта окна, `ORDER BY` внутри `OVER` задаёт последовательность. Эти части не меняют сами строки как обычный `GROUP BY`.

```sql
SELECT SalesOrderID, CustomerID, OrderDate,
       ROW_NUMBER() OVER
       (PARTITION BY CustomerID ORDER BY OrderDate, SalesOrderID) AS OrderNo
FROM Sales.SalesOrderHeader
ORDER BY CustomerID, OrderNo;
```

Контекст — `AdventureWorks2014`. Нумерация начинается с 1 для каждого покупателя. `SalesOrderID` разрешает равные даты. Без него два заказа в один момент могут получить разные номера в разных запусках.

**Пример вручную.** У A даты 1 и 3 января, у B — 2 января. Номера A: 1 и 2; номер B: 1. Покупатели не влияют на номера друг друга. Внешний `ORDER BY` здесь лишь делает последовательность наглядной.

Фильтр `WHERE OrderDate >= '20140101'` до окна начнёт нумерацию среди оставшихся заказов, а не среди всей истории. Если нужен исторический номер, сначала рассчитайте окно по истории в CTE, затем фильтруйте снаружи.

**Ошибка:** добавить `OrderDate` в `PARTITION BY`, когда хотели только упорядочить по дате. Это перезапустит расчёт для каждой даты покупателя и изменит смысл.

**Самопроверка.** Нужен ли `ORDER BY` для `SUM(...) OVER(PARTITION BY CustomerID)`? Для полного итога раздела нет. Добавление порядка может превратить его в накопление с рамкой по умолчанию.
