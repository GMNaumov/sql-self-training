# Секционирование и Columnstore в хранилищах

Большое хранилище выигрывает от продуманного жизненного цикла данных. Секционирование по времени помогает загружать и удалять части, columnstore — сжимать и агрегировать большие наборы. Это дополняющие, но разные механизмы.

**Пример скользящего окна.** Храним 36 месяцев продаж. Новый месяц сначала готовится в staging, проходит контроль количества и сумм, затем совместимая секция переключается в основную таблицу. Старейшая секция выводится по политике хранения. Все структуры, ограничения границ и индексы должны соответствовать требованиям `SWITCH`.

Для SQL Server 2014 clustered columnstore обновляемый, но без дополнительных rowstore-индексов на той же таблице. Некластерный columnstore ограничивает прямые DML-изменения. Нельзя копировать современную гибридную схему с обновляемым NCCI как готовое решение для этой версии.

Мелкие загрузки и множество удалённых строк могут ухудшать состояние columnstore; оценивайте группы строк и объём. Учебный `FactInternetSales` значительно меньше типичного промышленного факта: полезность структуры нужно проверять на подходящем масштабе.

**Порядок проверки:** одинаковый бизнес-результат, размер хранения, чтения, CPU, длительность отчётов, время загрузки и обслуживание. Фильтр по периоду должен позволять исключать ненужные секции, иначе они не дают ожидаемого сокращения чтения.

**Ошибка:** секционировать по столбцу, который не связан ни с запросами, ни с удалением данных. Усложнение само по себе не является оптимизацией. Подробные ограничения см. в [уроке Columnstore 2014](../../06-performance/09-columnstore-2014/README.md).
