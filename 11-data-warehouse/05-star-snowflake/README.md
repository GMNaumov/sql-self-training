# Схемы «звезда» и «снежинка»

Схема «звезда» (star schema) помещает факт в центр, а описательные измерения — вокруг него. В «снежинке» (snowflake) части измерений нормализованы в дополнительные таблицы. Оба подхода допустимы, но по-разному влияют на простоту запросов и сопровождение.

**Пример AdventureWorksDW:** продукт связан с подкатегорией, подкатегория — с категорией. Для суммы продаж по категории:

```sql
SELECT c.EnglishProductCategoryName, SUM(f.SalesAmount) AS Amount
FROM dbo.FactInternetSales AS f
JOIN dbo.DimProduct AS p ON p.ProductKey = f.ProductKey
JOIN dbo.DimProductSubcategory AS s
  ON s.ProductSubcategoryKey = p.ProductSubcategoryKey
JOIN dbo.DimProductCategory AS c
  ON c.ProductCategoryKey = s.ProductCategoryKey
GROUP BY c.ProductCategoryKey, c.EnglishProductCategoryName;
```

Контекст — DW. Внутренние соединения исключат продукты без заполненной цепочки категории; если они должны войти в отчёт, используйте согласованную обработку неизвестной категории, например внешние соединения и отдельную группу.

В звезде название категории могло бы храниться непосредственно в широком измерении продукта. Это уменьшает число соединений для пользователя, но ETL должен согласованно обслуживать атрибуты и историю.

**Ошибка:** называть всю AdventureWorksDW идеально чистой звездой и игнорировать дополнительные уровни. Опишите конкретные связи. Другая ошибка — соединять два факта напрямую по дате и продукту: несколько строк каждого дадут произведение. Сначала агрегируйте факты до общего зерна.

**Самопроверка.** Всегда ли снежинка быстрее из-за меньшего дублирования текста? Нет: хранение и стоимость выполнения нужно оценивать раздельно.
