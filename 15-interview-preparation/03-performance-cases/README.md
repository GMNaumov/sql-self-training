# Задачи по производительности

**Кейс 1.** Отчёт по месяцу читает много страниц. В `WHERE` стоят `YEAR(OrderDate)` и `MONTH(OrderDate)`, возвращаются все столбцы. Предложите диагностику, а затем изменение.

Сначала зафиксируйте параметры, строки, `STATISTICS IO/TIME`, фактический план и ожидания. Перепишите фильтр полуоткрытым диапазоном и перечислите нужные поля. Рассмотрите индекс по дате с необходимыми включёнными столбцами, учитывая уже существующие индексы и цену записи. Повторите измерение на коротком и широком диапазонах.

**Ожидаемое объяснение:** улучшение возможно из-за меньшего чтения и более подходящего доступа, но seek не гарантирован. Для почти всей таблицы scan может быть правильным. Без сервера нельзя назвать конкретную экономию миллисекунд.

**Кейс 2.** Одна процедура то быстрая, то медленная. У большинства клиентов один заказ, у одного — тысячи. Проверьте параметры компиляции и выполнения, расхождение строк и Lookup. Сравните характерные значения. Возможное точечное решение — recompile для проблемной команды, разделение сценариев или иной индекс; оцените CPU компиляции и другие вызовы.

**Кейс 3.** Запрос медленный, CPU почти не занят, ожидание `LCK_M_S`. Первой гипотезой должна быть блокировка: найдите блокировщика и незавершённую транзакцию. Rebuild или смена алгоритма соединения не устраняют чужую открытую транзакцию. RCSI рассматривают после оценки требований и `tempdb`, а не включают вслепую.

**Типичные ошибки ответа:** глобально очистить кеш, добавить `NOLOCK`, заставить все запросы идти параллельно или сериализовать, довериться процентам плана как фактическому времени. Хорошее решение связывает доказательство, причину, изменение и проверку на разных параметрах.
