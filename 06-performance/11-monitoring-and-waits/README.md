# Мониторинг производительности и статистика ожиданий

Статистика ожиданий (wait statistics) отвечает, чего ждали рабочие задачи сервера. Она помогает сузить поиск причины, но не является списком ошибок. Многие фоновые ожидания нормальны.

```sql
SELECT TOP (20) wait_type, waiting_tasks_count,
       wait_time_ms, signal_wait_time_ms
FROM sys.dm_os_wait_stats
ORDER BY wait_time_ms DESC;
```

Показатели накоплены после старта или сброса. Для интервала снимите два набора и вычислите разницу, проверив, что между ними не было рестарта или очистки. Не делайте вывод о текущем запросе из общего итога за месяц.

**Примеры направлений.** `LCK_M_*` ведёт к цепочке блокирования; `WRITELOG` — к подтверждению журнала и особенностям транзакций; `PAGEIOLATCH_*` — к загрузке страниц и объёму чтений; `SOS_SCHEDULER_YIELD` может сопровождать активную CPU-работу. `CXPACKET` в SQL Server 2014 требует анализа параллельных планов, а не автоматического `MAXDOP = 1`.

Сопоставляйте ожидания с длительностью запросов, CPU, чтениями, дисковыми задержками и параметрами. Один тип ожиданий имеет несколько причин: медленное подтверждение журнала может быть связано как с хранилищем, так и с большим числом крошечных commit.

**Самопроверка.** Почему первое место в списке не всегда цель оптимизации? Там может быть длительное штатное ожидание фонового потока. Нужны интервал, контекст и вклад в задержку пользовательской работы. Для чтения DMV нужны подходящие права, обычно `VIEW SERVER STATE`.
