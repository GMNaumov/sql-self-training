# Parameter Sniffing

Parameter sniffing — использование значений параметров при компиляции плана. Часто это полезно: оптимизатор знает, для какого покупателя строит запрос. Проблема возникает, когда план сохраняется и затем используется для сильно отличающихся значений.

**Пример.** Первый вызов процедуры ищет покупателя с одним заказом и получает план с Lookup. Второй вызов ищет крупного покупателя с тысячами заказов и повторно использует тот же план. Если бы компиляция началась с крупного покупателя, выбор мог быть другим.

В лаборатории сравните фактические планы и чтения для редкого и частого значения; посмотрите значения параметров при компиляции и выполнении в свойствах плана. Убедитесь, что задержка не вызвана блокировкой или вводом-выводом: один медленный параметр ещё не доказывает sniffing.

В SQL Server 2014 возможны точечный `OPTION (RECOMPILE)`, `OPTIMIZE FOR`, разделение разных сценариев и параметризованный динамический SQL. У каждого решения цена. Recompile тратит CPU каждый раз; оптимизация под одно значение может вредить другим; средняя оценка может не подходить ни одному краю распределения.

**Ошибка:** копировать параметр в локальную переменную как универсальное лечение. Это меняет доступную оценщику информацию, но не гарантирует правильную оценку. Автоматической Parameter Sensitive Plan optimization из SQL Server 2022 здесь нет.

**Самопроверка.** Надо ли полностью отключать использование параметров? Нет. Нужен план решения для конкретного распределения и частоты вызовов.
