# Проектирование индексов

Индекс проектируют под набор запросов и изменений. Ключевые столбцы задают порядок поиска; `INCLUDE` добавляет полезную нагрузку на листовой уровень, чтобы избежать обращений к основной строке. Покрывающий (covering) индекс содержит всё необходимое конкретному запросу.

На отдельной учебной копии таблицы можно сравнить:

```sql
CREATE INDEX IX_LabOrders_Customer_Date
ON dbo.LabOrders(CustomerID, OrderDate)
INCLUDE (SubTotal);
```

**Предусловие:** `dbo.LabOrders` — заранее созданная учебная таблица с этими столбцами и реалистичными данными; в AdventureWorks такого объекта нет. Запрос с `CustomerID = @id` и диапазоном `OrderDate` может воспользоваться порядком ключа. Один только фильтр по дате не получает такой же удобный начальный диапазон, потому что первый ключ — покупатель.

Фильтрованный индекс (filtered index), например по `WHERE Status = 1`, хранит подмножество строк. Он полезен для редких активных записей, если условие запроса логически соответствует фильтру и оптимизатор может это доказать. Параметризация может осложнить такое доказательство.

Не добавляйте в `INCLUDE` все столбцы автоматически. Каждый индекс занимает место, увеличивает журнал и стоимость вставок, обновлений и удаления. Совмещайте близкие потребности, но не пытайтесь покрыть абсолютно всё одним широким индексом.

**Самопроверка.** Почему предложение Missing Index из плана не является готовым решением? Оно оценивает конкретную оптимизацию и не учитывает полностью существующий набор индексов, цену записи и другие запросы. Сравните пользу на рабочей нагрузке.
